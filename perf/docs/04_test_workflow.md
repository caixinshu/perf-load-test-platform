# 性能测试基本流程

> Day 1 学习笔记 · 8 步基本流程

---

## 一、8 步流程总览

```
┌─────────────┐
│ 1. 需求分析  │ ← 明确测试目标、场景、指标要求
└──────┬──────┘
       ▼
┌─────────────┐
│ 2. 环境准备  │ ← 被测环境 + 压测机 + 监控工具
└──────┬──────┘
       ▼
┌─────────────┐
│ 3. 脚本开发  │ ← 编写压测脚本、调试、参数化
└──────┬──────┘
       ▼
┌─────────────┐
│ 4. 基准测试  │ ← 建立基线数据，作为后续对比参照
└──────┬──────┘
       ▼
┌─────────────┐
│ 5. 场景测试  │ ← 按计划执行各种性能测试场景
└──────┬──────┘
       ▼
┌─────────────┐
│ 6. 瓶颈定位  │ ← 分析性能瓶颈，定位到具体模块
└──────┬──────┘
       ▼
┌─────────────┐
│ 7. 优化验证  │ ← 修复后重新测试，对比优化效果
└──────┬──────┘
       ▼
┌─────────────┐
│ 8. 报告输出  │ ← 整理测试结果，输出性能测试报告
└─────────────┘
```

---

## 二、各步骤详细说明

### Step 1: 需求分析

| 分析项 | 内容 | 示例 |
|--------|------|------|
| 测试目标 | 为什么要测 | 上线前验证 / 容量规划 / 对比优化 |
| 测试场景 | 测哪些接口 | 商品列表查询 + 创建商品 |
| 指标要求 | 达到什么标准 | TPS > 500，P95 < 200ms |
| 用户模型 | 模拟什么行为 | 60% 浏览 + 30% 创建 + 10% 查询 |
| 数据量 | 多少测试数据 | 10 万条商品数据 |

### Step 2: 环境准备

| 组件 | 说明 | 工具 |
|------|------|------|
| 被测环境 | 运行被测服务 | Docker + docker-compose |
| 压测机 | 运行 k6 压测脚本 | k6（独立机器或同机学习用） |
| 监控工具 | 采集系统指标 | Prometheus + node_exporter |
| 可视化 | 展示性能数据 | Grafana |

**注意事项**：
- 压测机和被测服务最好分开部署，避免互相影响
- 本地学习可以同机，但要意识到结果不严谨
- 监控必须准备好，否则跑完不知道瓶颈在哪

### Step 3: 脚本开发

| 开发项 | 说明 | k6 对应 |
|--------|------|---------|
| 基础请求 | GET/POST 调用 | `http.get()` / `http.post()` |
| 参数化 | 动态数据 | `randomIntBetween()` / SharedArray |
| 检查点 | 响应断言 | `check(res, { ... })` |
| 思考时间 | 模拟用户停顿 | `sleep(1)` |
| 分组 | 请求分组统计 | `group('名称', function() { ... })` |
| 阶段 | 加压模式 | `stages: [...]` |
| 阈值 | 通过/失败标准 | `thresholds: { ... }` |

### Step 4: 基准测试

- 用固定低负载跑 3 次
- 记录每次的 TPS、P50、P95、P99、错误率
- 3 次偏差 < 10% 取平均值作为基线
- 后续所有测试结果和基线对比

### Step 5: 场景测试

按计划执行：
1. 负载测试：验证预期负载达标
2. 压力测试：找到系统极限
3. 稳定性测试：长时间运行检查泄漏
4. 尖峰测试：验证突发流量
5. （可选）容量测试：大数据量性能

### Step 6: 瓶颈定位

四层分析法：
```
请求 → [网络层] → [应用层] → [数据库] → [存储层]
```

| 层级 | 排查工具 | 典型瓶颈 |
|------|----------|----------|
| 网络 | ping / tcpdump | 带宽不足 |
| 应用 | top / py-spy | CPU 100%、内存泄漏 |
| 数据库 | EXPLAIN / slow_log | 慢查询、锁竞争 |
| 存储 | iostat | 磁盘 I/O 饱和 |

### Step 7: 优化验证

- 修复后用**相同**的脚本和配置重新测试
- 对比优化前后的基线数据
- 验证优化是否有效，有无引入新问题
- 记录优化前后的对比数据

### Step 8: 报告输出

性能测试报告应包含：
1. 测试概述（目标、环境、工具）
2. 测试场景和脚本说明
3. 基线数据
4. 各场景测试结果
5. 瓶颈分析和定位过程
6. 优化建议和验证结果
7. 结论和建议

---

## 三、流程关键原则

1. **先基线后测试**：没有基线就无法判断好坏
2. **先监控后压测**：没有监控就不知道瓶颈在哪
3. **单一变量**：每次只改一个条件，否则不知道哪个有效
4. **多次取稳定值**：单次结果有偶然性
5. **对比验证**：优化后必须和基线对比
