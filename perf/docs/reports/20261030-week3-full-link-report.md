# 全链路压测报告

> 项目二 · 第 3 周 · 多服务全链路压测 + 分布式压测 + 链路追踪
> 报告日期：2026-10-30
> 被测系统：API 网关 + 商品服务 + 订单服务 + PostgreSQL + Redis + Jaeger

---

## 一、测试背景和目标

### 1.1 背景

前两周完成了单接口、单服务的性能测试。但真实生产系统是多服务协作的——前端、网关、业务服务、数据库、缓存、消息队列……全链路压测就是模拟真实用户的完整操作路径，串联所有依赖服务，找到整个链路中的瓶颈。

本周搭建了多服务场景（网关 + 商品服务 + 订单服务 + DB + Redis），接入了 Jaeger 链路追踪，实现了从「单接口压测」到「全链路压测」的跃迁。

### 1.2 测试目标

| 目标 | 说明 |
|------|------|
| 验证多服务链路正确性 | 一次下单请求经过 gateway → order → product → db/redis 5 个节点 |
| 建立全链路性能基线 | 在低负载下获取各服务、各接口的性能基准 |
| 定位全链路瓶颈 | 通过 Jaeger 链路追踪 + 系统资源监控，找到瓶颈节点 |
| 验证分布式压测能力 | 3 实例 k6 集群分片压测，结果聚合 |
| 数据库压测与慢查询分析 | 识别慢 SQL，验证索引优化效果 |

### 1.3 测试范围

- **包含**：商品浏览、下单、订单查询三大核心链路；PostgreSQL 读写；Redis 缓存
- **不包含**：消息队列、分布式锁、服务熔断降级（后续迭代）

### 5.2 负载测试（100 VU 稳定）

### 5.3 压力测试（200 VU）

| 指标 | 值 | 状态 |
|------|-----|------|
| RPS | ~420 | - |
| p95 | 1,350 ms | ❌ > 800ms |

**结论**：系统在 200 VU 下超过阈值，瓶颈出现在数据库层（连接池竞争 + 慢查询）。

| 操作 | RPS | p95 | 错误率 |

**结论**：模糊搜索（`LIKE '%xxx%'`）是最大瓶颈，p95 达 2.5s，错误率 8%。

## 六、全链路瓶颈分析

### 6.1 Jaeger 链路分析（6 个维度）

| 维度 | 分析方法 | 发现 |
|------|---------|------|
| **总耗时分布** | 看 trace 总时长 waterfall | product-service 占 65%，order 占 25%，gateway 占 10% |
| **关键路径** | 找最长 span 链 | DB 查询是关键路径，缓存命中时跳过 |
| **服务耗时** | 按 service 聚合 | product-service DB span 平均 80ms |
| **Span 耗时 Top5** | 排序 span duration | 1) searchProduct SQL 2) listProducts SQL 3) createProduct INSERT |
| **错误 Span** | 过滤 status=error | 集中在 searchProduct 的 DB 超时 |
| **并发影响** | 高 VU 下对比 span 数 | 200 VU 时 DB span 排队等待明显 |

### 6.2 系统资源分析

| 资源 | 100 VU | 200 VU | 是否瓶颈 |
|------|--------|--------|---------|
| API Gateway CPU | 25% | 45% | 否 |
| Product Service CPU | 40% | 70% | 临界 |
| Order Service CPU | 30% | 55% | 否 |
| PostgreSQL CPU | 50% | 92% | **是** |
| 内存 | 正常 | 正常 | 否 |
| 网络 | 正常 | 正常 | 否 |

### 6.3 瓶颈定位

**主瓶颈：PostgreSQL**
- CPU 在 200 VU 下达 92%
- 慢查询（模糊搜索）占 DB 时间 70%
- 连接池使用率在 200 VU 下达 85%

**次瓶颈：Product Service DB 连接管理**
- 每个请求创建新连接（无连接池）
- 高并发下连接创建开销大

## 七、瓶颈定位结论 + 证据

### 7.1 瓶颈 1：模糊搜索无索引

**现象**：`GET /products?search=test` p95 = 2.5s，错误率 8%

**证据**（EXPLAIN ANALYZE）：
```
Seq Scan on products
  Filter: (name ~~ '%test%'::text)
  Rows Removed by Filter: 9990
  Execution Time: 12.5 ms   -- 单条快，但高并发下排队
```

**根因**：`LIKE '%xxx%'` 前导模糊查询无法使用 B-tree 索引，全表扫描。

### 7.2 瓶颈 2：DB 连接无池化

**现象**：高并发下响应时间飙升，DB CPU 不高但等待长

**证据**：Jaeger span 显示 product-service DB connect 耗时占请求总耗时 30%。

**根因**：`get_db()` 每次创建新 psycopg2 连接，TCP 握手 + 认证开销大。

### 7.3 瓶颈 3：log_statement=all 开销

**现象**：压测时 PG 日志写入量大，I/O wait 上升

**证据**：`log_statement=all` 记录每条 SQL，磁盘 I/O 成为瓶颈。

**根因**：全量 SQL 日志在高并发下 I/O 开销显著。

## 八、优化建议

### 8.1 短期优化（1-3 天）

| 优化项 | 预期收益 | 实施难度 |
|--------|---------|---------|
| 搜索接口加 GIN 索引（pg_trgm） | 搜索 p95 降 80% | 低 |
| 引入连接池（psycopg2.pool） | 连接耗时降 70% | 中 |
| 缓存空值防穿透 | 缓存命中率 +15% | 低 |
| log_statement 改为 ddl | PG I/O 降 60% | 低 |

### 8.2 中期优化（1-2 周）

| 优化项 | 预期收益 | 实施难度 |
|--------|---------|---------|
| 商品列表分页加游标 | 深翻页性能提升 | 中 |
| Redis 热点 key 永不过期 | 防缓存击穿 | 低 |
| 订单服务异步化 | 下单链路缩短 40% | 中 |
| 读写分离 | 读性能提升 2x | 高 |

### 8.3 长期优化（1 月+）

| 优化项 | 预期收益 | 实施难度 |
|--------|---------|---------|
| 商品搜索迁 Elasticsearch | 搜索能力质的飞跃 | 高 |
| 数据库分库分表 | 突破单表瓶颈 | 高 |
| 服务网格化（Service Mesh） | 全链路可观测 | 高 |

## 九、优化前后对比

### 9.1 搜索接口优化（GIN 索引）

```sql
CREATE EXTENSION pg_trgm;
CREATE INDEX idx_products_name_trgm ON products USING gin (name gin_trgm_ops);
```

| 指标 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| p95 响应时间 | 2,500 ms | 180 ms | 93% ↓ |
| RPS | 15 | 120 | 8x ↑ |
| 错误率 | 8% | 0.3% | 96% ↓ |

### 9.2 连接池优化

| 指标 | 优化前 | 优化后 | 提升 |
|------|--------|--------|------|
| DB 连接耗时 | 30ms | 2ms | 93% ↓ |
| p95 全链路 | 1,350 ms | 850 ms | 37% ↓ |
| 200 VU 错误率 | 4.8% | 1.5% | 69% ↓ |

### 9.3 综合优化后

| 场景 | 优化前 p95 | 优化后 p95 | 状态 |
|------|-----------|-----------|------|
| 100 VU 全链路 | 620 ms | 310 ms | ✅ |
| 200 VU 全链路 | 1,350 ms | 680 ms | ✅ < 800ms |
| 200 VU 错误率 | 4.8% | 1.2% | ✅ < 3% |

## 十、风险和后续建议

### 10.1 风险

| 风险 | 等级 | 应对 |
|------|------|------|
| 连接池配置不当（过大/过小） | 中 | 压测验证最佳值 |
| 缓存击穿（热点 key 过期） | 中 | 热点 key 永不过期 + 互斥锁 |
| 分布式压测数据倾斜 | 低 | 分片 ID 均匀分配 |
| Jaeger 采样丢失 | 低 | 确认 AlwaysOnSampler |
| PG 慢查询日志误删 | 低 | 定期归档日志 |

### 10.2 后续建议

1. **性能门禁**：在 CI 中设置 p95 < 800ms、错误率 < 3% 的硬门禁，回归即拦截
2. **定期压测**：每次重大变更后跑全链路压测，对比基线
3. **混沌工程**：模拟 Redis 宕机、DB 慢查询等故障，验证降级能力
4. **容量规划**：基于压测数据推算单机 TPS 上限，做容量规划
5. **链路追踪常态化**：Jaeger 接入告警，慢 trace 自动通知
