# 22. 数据库压测与慢查询分析（Week 3 Day 19）

## 一、为什么数据库性能测试最重要

很多系统的最终瓶颈都是数据库：
- 应用层可以横向扩容（加机器），但数据库扩容成本很高
- 慢 SQL 是最常见的性能问题，也是优化收益最大的地方
- DBA 的核心工作之一就是 SQL 优化

**全链路压测中，数据库往往是最后一公里的瓶颈。**

## 二、数据库 7 个核心性能指标

| 指标 | 含义 | 参考阈值 | 监控方式 |
|------|------|---------|---------|
| **QPS** | 每秒查询数 | 根据业务量定 | `pg_stat_database.xact_commit` |
| **TPS** | 每秒事务数 | 根据业务量定 | `pg_stat_database.xact_commit + xact_rollback` |
| **响应时间** | SQL 平均/分位执行时间 | p95 < 100ms | 慢查询日志 / `pg_stat_statements` |
| **连接数** | 活跃连接数 / 最大连接数 | < 80% max_connections | `pg_stat_activity` |
| **慢查询数** | 超过阈值的 SQL 数量 | 越少越好 | `log_min_duration_statement` |
| **锁等待** | 等待锁的事务数 | < 5 | `pg_locks` |
| **缓存命中率** | shared buffer 命中比例 | > 99% | `pg_statio_user_tables` |

### 关键阈值说明

- **响应时间 p95 < 100ms**：OLTP 系统的常见标准，超过说明需要优化
- **连接数 < 80%**：留余量给突发流量，连接打满会导致新请求直接失败
- **缓存命中率 > 99%**：低于这个值说明内存不够，频繁读磁盘

## 三、PostgreSQL 慢查询日志配置

在 `docker-compose.services.yml` 中给 PostgreSQL 加配置：

```yaml
db:
  image: postgres:15-alpine
  command:
    - "postgres"
    - "-c"
    - "log_statement=all"                    # 记录所有 SQL
    - "-c"
    - "log_min_duration_statement=100"       # 超过 100ms 的 SQL 记为慢查询
    - "-c"
    - "shared_buffers=256MB"
```

### 慢查询阈值怎么定？

`log_min_duration_statement = 100` 表示执行时间超过 100 毫秒的 SQL 会被记录。

| 场景 | 建议阈值 |
|------|---------|
| 高并发 OLTP（电商、支付） | 50ms |
| 普通业务系统 | 100ms |
| 低并发后台系统 | 500ms |
| 报表/分析查询 | 1000ms+ |

### 查看慢查询日志

```bash
# Docker 环境
docker compose -f docker-compose.services.yml logs db | grep "duration"

# 输出示例：
# 2026-10-30 10:00:00.123 UTC [123] LOG:  duration: 250.123 ms  statement: SELECT * FROM products WHERE name LIKE '%test%'
```

## 五、EXPLAIN 分析慢查询

### EXPLAIN ANALYZE 用法

```sql
-- 查看 SQL 执行计划（真实执行）
EXPLAIN ANALYZE SELECT * FROM products WHERE name LIKE '%test%';
```

### 输出解读

**无索引时（全表扫描）：**
```
Seq Scan on products  (cost=0.00..25.50 rows=1000 width=50) (actual time=0.05..12.5 rows=50 loops=1)
  Filter: (name ~~ '%test%'::text)
  Rows Removed by Filter: 950
Planning Time: 0.1 ms
Execution Time: 12.5 ms
```

| 字段 | 含义 |
|------|------|
| `Seq Scan` | 全表扫描（坏） |
| `Rows Removed by Filter: 950` | 扫描了 1000 行，过滤掉 950 行 |
| `Execution Time: 12.5 ms` | 实际执行时间 |

**加 B-tree 索引后（前缀匹配）：**
```sql
CREATE INDEX idx_products_name ON products(name);
EXPLAIN ANALYZE SELECT * FROM products WHERE name LIKE 'test%';
```
```
Index Scan using idx_products_name on products  (actual time=0.02..0.5 rows=10 loops=1)
  Index Cond: ((name)::text ~>=~ 'test'::text)
Execution Time: 0.5 ms  ← 快了 25 倍！
```

### 执行计划关键字

| 关键字 | 含义 | 好坏 |
|--------|------|------|
| `Index Scan` | 走索引 | ✅ 好 |
| `Seq Scan` | 全表扫描 | ❌ 数据量大时慢 |
| `Index Only Scan` | 只查索引不查表 | ✅ 最好 |
| `Bitmap Index Scan` | 位图索引扫描 | ✅ 好 |
| `Nested Loop` | 嵌套循环连接 | 小表好，大表慢 |
| `Hash Join` | 哈希连接 | 大表连接好 |
| `Sort` | 排序 | 数据量大时慢 |
| `Materialize` | 物化子查询 | 可能慢 |

## 六、索引优化实战

### 场景：模糊搜索性能对比

**优化前（无索引，前后模糊 `%test%`）：**
```sql
EXPLAIN ANALYZE SELECT * FROM products WHERE name LIKE '%test%';
-- Seq Scan, Execution Time: 12.5 ms
```

**加 B-tree 索引后（前缀模糊 `test%`）：**
```sql
CREATE INDEX idx_products_name ON products(name);
EXPLAIN ANALYZE SELECT * FROM products WHERE name LIKE 'test%';
-- Index Scan, Execution Time: 0.5 ms  ← 25 倍提升
```

**前后模糊 `%test%` 仍走全表扫描：**
```sql
EXPLAIN ANALYZE SELECT * FROM products WHERE name LIKE '%test%';
-- Seq Scan, Execution Time: 12.5 ms  ← 没变！
```

### 索引的局限

| 查询模式 | B-tree 索引 | 解决方案 |
|---------|------------|---------|
| `WHERE name = 'test'` | ✅ 有效 | B-tree |
| `WHERE name LIKE 'test%'` | ✅ 有效 | B-tree（前缀匹配） |
| `WHERE name LIKE '%test'` | ❌ 无效 | 反转列 + 索引，或全文索引 |
| `WHERE name LIKE '%test%'` | ❌ 无效 | GIN 全文索引 / Elasticsearch |
| `WHERE LOWER(name) = 'test'` | ❌ 无效 | 表达式索引 `CREATE INDEX ... ON (LOWER(name))` |

**索引不是银弹**，要理解每种索引的适用场景。对于 `%xxx%` 前后模糊查询，B-tree 索引无效，需要：
- PostgreSQL GIN 全文索引：`CREATE INDEX ... ON products USING gin(to_tsvector('english', name));`
- 或者上 Elasticsearch

## 七、6 种常见数据库优化手段

### 1. 连接池优化

合理设置连接池大小，避免连接数不够（请求排队）或过多（DB 资源耗尽）。

```python
# psycopg2 连接池
from psycopg2 import pool
connection_pool = pool.ThreadedConnectionPool(
    minconn=5, maxconn=20,  # 最小5，最大20
    host="db", dbname="demo", user="demo", password="demo123"
)
```

**经验公式**：`max_connections = ((核心数 * 2) + 有效磁盘数)`，一般 100-300。

### 2. SQL 优化

- 避免 `SELECT *`，只查需要的列
- 避免 N+1 查询，用 JOIN 代替多次查询
- 用 `LIMIT` 限制返回行数
- 避免在 WHERE 中对列用函数（`WHERE YEAR(created_at) = 2026` → 全表扫描）

### 3. 读写分离

读多写少的场景，读走从库，写走主库。

```
写请求 → 主库（Master）
读请求 → 从库（Slave）  ← 主从同步有延迟，注意一致性
```

### 4. 分库分表

单表数据量太大（千万级以上）时考虑分表：
- 水平分表：按 ID 范围或 Hash 分表
- 垂直分表：把大字段拆到单独的表

### 5. 缓存

热点数据放 Redis，减轻数据库压力。

```python
# 先查缓存
cached = redis.get(f"product:{id}")
if cached:
    return json.loads(cached)
# 缓存未命中查 DB，写缓存
product = db.query(...)
redis.setex(f"product:{id}", 60, json.dumps(product))
```

### 6. 异步化

非核心操作异步处理，降低主链路耗时。

```
下单主链路：扣库存 → 创建订单（同步，必须快）
异步操作：发通知、记日志、统计报表（MQ 异步，不影响主链路）
```
