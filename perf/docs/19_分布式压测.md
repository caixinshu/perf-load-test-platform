# 分布式压测（k6 集群）— Week 3 Day 16

## 为什么需要分布式压测

单机压测有天花板：
- 一台压测机的 CPU、网络、端口数有限
- 当目标 TPS 超过单机能力，**压测机先成为瓶颈**，测出的结果不准
- 真实用户分布在各地，单机房压测无法模拟网络延迟差异
- 大流量场景（几万、几十万 TPS）只能靠多机集群

## k6 分布式方案

| 方案 | 适用场景 | 说明 |
|------|---------|------|
| k6 Cloud | 商业 | Grafana 官方 SaaS，全球分布式节点 |
| k6 Operator | Kubernetes | 生产级，CRD 管理压测任务 |
| **Docker Compose 多实例** | **本地学习** | 本周采用，原理与 k8s 一致 |
| 多机手动协调 | 土法 | SSH 起多个 k6 实例 |

## 分片（Sharding）原理

把测试数据和 VU 切成 N 份，每个 k6 实例只跑自己那一份，避免数据冲突。

```
3 个 worker，总 VU = 150
┌─────────────┬─────────────┬─────────────┐
│  worker-0   │  worker-1   │  worker-2   │
│  50 VU      │  50 VU      │  50 VU      │
│  SHARD_ID=0 │  SHARD_ID=1 │  SHARD_ID=2 │
│  ID 1-1000  │  ID 10001+  │  ID 20001+  │
└─────────────┴─────────────┴─────────────┘
         ↓ 各自请求 api-gateway:8000 ↓
              [被测服务集群]
```

关键环境变量：
- `SHARD_ID` — 当前实例编号（0, 1, 2）
- `SHARD_COUNT` — 总实例数

脚本中按分片分配数据段：
```js
const USER_ID_BASE = SHARD_ID * 10000;
const userId = USER_ID_BASE + randomIntBetween(1, 1000);
```

## 运行方式

### Docker 分布式（推荐 CI）

```bash
docker compose -f docker-compose.distributed.yml up --build
```

3 个 worker 并行压测，完成后 aggregator 自动聚合结果，输出到 `k6-results` volume。

### 本地单实例（验证脚本逻辑）

```bash
# Windows
$env:SHARD_ID="0"; $env:SHARD_COUNT="1"; $env:GATEWAY_URL="http://127.0.0.1:8000"
k6 run perf/scripts/09-distributed-load-test.js
```

### 结果聚合（手动）

```bash
python scripts/aggregate_k6_results.py ./perf/results/distributed
```

## 验证结果

### 本地语法验证

```bash
# k6 脚本语法
k6 inspect perf/scripts/09-distributed-load-test.js   # ✅ 解析成功，stages 正确

# Python 聚合脚本

```

### CI 验证

GitHub Actions `distributed-test.yml` 自动执行：
1. 启动 5 节点被测服务，健康检查 + 下单冒烟
2. 3 个 k6 worker 分片压测（总 150 VU）
3. 从共享 volume 拷贝结果，运行聚合脚本
4. 断言 `aggregated-summary.json` 存在且 `http_req_duration.count > 0`
5. 上传结果 artifact

## 踩坑记录

| 问题 | 原因 | 解决 |
|------|------|------|
| k6 脚本依赖 jslib.k6.io | 外网导入离线不可用 | 自实现 `randomIntBetween`，用 `Math.random()` |
| `depends_on` 不等 worker 跑完 | docker compose 只保证启动顺序 | CI 中用 `--abort-on-container-exit` 等待 worker 退出 |
| 聚合结果在 volume 里 | 容器结束后文件留在 volume | CI 中用 `docker cp` 从临时容器拷出 |
| `volumes_from` 已废弃 | 旧版 docker-compose 语法 | 改用共享 named volume `k6-results` |

## 关键指标解读

聚合后的 `http_req_duration` p(95) 是全链路下单的端到端延迟，包含：
- gateway 转发
- order-service 处理
- product-service 查询（含缓存命中/未命中）
- PostgreSQL 写入

与单服务压测的 p(95) 对比，可以看出链路中每个环节的开销占比。
