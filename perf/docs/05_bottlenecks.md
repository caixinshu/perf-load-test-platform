# 常见性能瓶颈类型

> Day 1 学习笔记 · 6 类性能瓶颈 + 现象

---

## 一、6 类性能瓶颈

| 瓶颈类型 | 现象 | 典型原因 | 排查工具 |
|----------|------|----------|----------|
| CPU 瓶颈 | CPU 使用率持续 100%，TPS 上不去 | 计算密集、算法差、GIL | top / htop / py-spy |
| 内存瓶颈 | 内存不足导致频繁 GC 或 OOM | 内存泄漏、大对象、缓存无上限 | free / vmstat / memory_profiler |
| IO 瓶颈 | 磁盘读写慢，数据库查询慢 | 慢查询、大量小文件、日志写入 | iostat / iotop |
| 网络瓶颈 | 带宽不足，传输延迟大 | 小包过多、带宽不够、跨区域 | iftop / tcpdump |
| 应用瓶颈 | 代码逻辑慢、锁竞争、连接池不足 | 同步阻塞、锁竞争、线程池满 | 火焰图 / py-spy |
| 数据库瓶颈 | 慢 SQL、死锁、连接数不足 | 缺索引、N+1 查询、连接池耗尽 | EXPLAIN / slow_query_log |

---

## 二、各类瓶颈详细分析

### 1. CPU 瓶颈

**现象**：
- `top` 显示 CPU 使用率持续 > 90%
- 增加 VU 但 TPS 不再增长
- 响应时间随 VU 线性增长

**典型原因**：
- 计算密集型任务（加密、压缩、序列化）
- 算法复杂度高（O(n²) 变成 O(n log n)）
- Python GIL 限制多线程并发
- 频繁的正则匹配 / JSON 解析

**排查路径**：
```
top → 确认 CPU 100% → py-spy record → 火焰图 → 找到热点函数
```

**优化方向**：
- 优化算法复杂度
- 使用 C 扩展（Cython / C Extension）
- 多进程替代多线程（绕过 GIL）
- 引入缓存减少重复计算

---

### 2. 内存瓶颈

**现象**：
- `free` 显示可用内存持续下降
- 频繁 GC 导致响应时间波动
- 长时间运行后 OOM（Out of Memory）
- 稳定性测试中 RT 逐渐升高

**典型原因**：
- 内存泄漏（对象引用未释放）
- 大对象未及时回收（大列表 / 大字典）
- 缓存无上限（dict 越来越大）
- 连接对象泄漏（未关闭的数据库连接）

**排查路径**：
```
free -m → 确认内存下降 → memory_profiler → 定位泄漏对象
→ 长时间运行后 tracemalloc 对比快照
```

**优化方向**：
- 使用 `weakref` 弱引用
- 限制缓存大小（LRU Cache）
- 及时关闭连接（`with` 语句）
- 定期重启进程（兜底方案）

---

### 3. IO 瓶颈

**现象**：
- `iostat` 显示磁盘 util > 90%
- 数据库查询慢但 CPU 不高
- 大量等待 I/O 的进程
- 响应时间波动大

**典型原因**：
- 慢查询导致大量磁盘读
- 大量小文件写入（日志 / 临时文件）
- 数据库未命中索引导致全表扫描
- 同步写日志阻塞主线程

**排查路径**：
```
iostat -x 1 → 确认 I/O 高 → iotop → 找到 I/O 大的进程
→ 数据库 EXPLAIN → 确认是否全表扫描
```

**优化方向**：
- 添加数据库索引
- 异步写日志（logging handlers）
- SSD 替换 HDD
- 读写分离

---

### 4. 网络瓶颈

**现象**：
- `iftop` 显示带宽接近上限
- 跨区域请求延迟高
- 大量 TIME_WAIT 连接
- 连接建立时间长

**典型原因**：
- 小包过多（频繁小请求）
- 带宽不足
- 跨机房 / 跨区域调用
- 连接未复用（每次新建 TCP 连接）

**排查路径**：
```
iftop → 确认带宽 → tcpdump → 分析包大小和频率
→ netstat -n | grep TIME_WAIT → 确认连接复用
```

**优化方向**：
- 合并小请求（批量接口）
- 使用 HTTP Keep-Alive
- 启用连接池
- CDN 加速静态资源

---

### 5. 应用瓶颈

**现象**：
- CPU 和内存都不高，但响应慢
- 某些请求特别慢（P99 高但 P50 低）
- 并发量上不去但资源没用满

**典型原因**：
- 同步阻塞调用（同步 HTTP 请求）
- 锁竞争（多个线程争抢同一把锁）
- 连接池配置太小
- 序列化/反序列化耗时

**排查路径**：
```
py-spy record → 火焰图 → 找到耗时函数
→ 检查是否有同步阻塞 → 检查锁竞争
```

**优化方向**：
- 异步化（async/await）
- 减小锁粒度
- 增大连接池
- 使用更快的序列化格式（MessagePack）

---

### 6. 数据库瓶颈

**现象**：
- 数据库 CPU 高但应用 CPU 不高
- 慢查询日志有大量记录
- 连接池经常耗尽
- 某些查询响应时间极长

**典型原因**：
- 缺少索引导致全表扫描
- N+1 查询问题
- 死锁
- 连接数配置不合理
- 大表 JOIN

**排查路径**：
```
慢查询日志 → 找到慢 SQL → EXPLAIN ANALYZE → 确认执行计划
→ 检查索引 → 检查 JOIN → 检查连接池配置
```

**优化方向**：
- 添加合适的索引
- 优化 SQL（避免 SELECT *）
- 解决 N+1（JOIN 或批量查询）
- 读写分离
- 分库分表（终极方案）

---

## 三、瓶颈定位决策树

```
TPS 上不去 / RT 高
     │
     ├─ CPU > 90%? ───→ CPU 瓶颈 ──→ 火焰图定位热点
     │
     ├─ 内存不足? ────→ 内存瓶颈 ──→ memory_profiler 定位泄漏
     │
     ├─ 磁盘 I/O 高? ─→ IO 瓶颈 ───→ iostat + 慢查询定位
     │
     ├─ 网络带宽满? ──→ 网络瓶颈 ──→ iftop + 合并请求
     │
     ├─ DB CPU 高? ───→ 数据库瓶颈 → EXPLAIN + 加索引
     │
     └─ 都不高但慢? ──→ 应用瓶颈 ──→ py-spy + 检查锁/阻塞
```

---

## 四、一句话总结

> 六类瓶颈——CPU（算不动）、内存（装不下）、IO（读写慢）、网络（传不动）、应用（代码慢）、数据库（查询慢）。定位方法：先看资源利用率判断方向，再用工具定位到具体函数/SQL，最后用优化手段验证效果。
