# 10 - 基线建立与性能门禁（Day 6）

> 目标：把"压测结果"升级为"性能门禁"。
> 门禁值不能拍脑袋，必须来自实测基线；而基线必须可复现——否则今天定 500ms、明天定 2s，门禁就成了摆设。

---

## 一、门禁值从哪来：一条公式

```
性能门禁 = 实测基线 × 1.5
```

| 要素 | 含义 | 不这么做的后果 |
|------|------|---------------|
| **实测基线** | 在**受控条件下**重复测量得到的稳定值 | 拍脑袋定阈值：要么天天误报，要么形同虚设 |
| **× 1.5** | 留 50% 余量，吸收正常抖动（GC、调度、机器差异） | 余量为 0：一次 GC 就让流水线红；余量过大：劣化 3 倍都不报警 |
| **受控条件** | 环境、数据量、负载形状三样都要固定 | 变量没锁住，测出来的"基线"其实是噪声 |

Day 3 的第一次负载测试把门禁写成 `p(95)<500ms`，这个 500ms 是"合理的对外 SLA 期望值"，
不是"实测基线"。结果 CI 一直红着，只能挂 `continue-on-error` 观察。Day 6 要做的就是补上这块。

---

## 二、测量条件（控制变量）

| 维度 | 取值 | 说明 |
|------|------|------|
| 机器 | Windows 本机，k6 与被测服务同机 | ⚠️ k6 和服务抢 CPU，绝对值会比独立压测机高 |
| 被测服务 | `quality-pipeline-demo`（FastAPI + SQLite，uvicorn 单 worker） | 每个请求新建/关闭 SQLite 连接（已知瓶颈） |
| **数据集** | **固定 200 条，每轮开跑前重置** | 关键控制项，见第四节 |
| 冒烟脚本 | `01-simple-get.js`，10 VU / 30s 循环 | 纯读 `GET /items` |
| 负载脚本 | `02-load-test.js`，stages 三段式 20 VU / 3min | 读 + 写混合（4 个请求/迭代） |
| 重复次数 | 每个脚本连续跑 3 次 | Day 4 定的规矩：3 次接近才算稳定 |

## 三、第一次尝试：没控住数据集，基线是"漂移"的

第一次按计划直接连跑 3 次负载测试。结果是：

| 轮次 | 开跑时数据量 | p50 | p90 | **p95** | TPS | 失败率 | checks |
|------|------------|-----|-----|--------|-----|--------|--------|
| 1 | 1619 条 | 171.28 ms | 609.45 ms | **1.27 s** | 12.46 | 0.17% | 99.82% |
| 2 | 2751 条 | 180.81 ms | 806.28 ms | **1.81 s** | 11.70 | 0.23% | 99.78% |
| 3 | 3825 条 | 212.60 ms | 832.08 ms | **1.66 s** | 11.48 | 0.14% | 99.86% |

**p95 偏差 = (1.81 − 1.27) / 1.27 ≈ 42%**，远超 Day 4 定的 ±10% 稳定线。

### 根因：数据集在测试过程中自己长大

`02-load-test.js` 有两条写路径（场景2 创建商品、场景3 的查询前置创建），每个迭代写入 2 条数据：

```
运行前 1619 条  →  第1轮 +1132 条 → 第2轮 +1074 条 → 第3轮 +1042 条  →  结束时 4867 条
```

而 `GET /items` 是 `SELECT * FROM items` 全表返回、**无分页**：

```python
@app.get("/items")
def list_items():
    conn = sqlite3.connect(DB_PATH)
    cursor = conn.execute("SELECT * FROM items")   # ← 全表，返回体随数据量线性增长
    items = [{"id": r[0], "name": r[1], "price": r[2]} for r in cursor]
    conn.close()
    return items
```

于是每一轮都比上一轮"更重"：读接口要在更大的结果集上做 SQLite 全表扫描 + Python 序列化 + JSON 传输。
**p95 的上升不是系统劣化，而是测试输入变了。**

> 这正是性能测试最经典的坑：**被测对象状态在测试之间发生了变化，导致多轮结果不可比。**
> 结论：**基线测量必须固定数据集，且每轮开跑前重置。**

## 四、第二次尝试：固定数据集后的受控测量

每轮开跑前把库重置为固定 200 条（`DELETE FROM items` + 重新灌入），其余条件不变。

### 冒烟基线（`01-simple-get.js`，10 VU / 30s，纯读）

| 轮次 | avg | p50 | p90 | **p95** | TPS | 失败率 | checks |
|------|-----|-----|-----|---------|-----|--------|--------|
| 1 | 11.51 ms | 8.78 ms | 15.28 ms | **20.52 ms** | 9.83 | 0% | 100% |
| 2 | 11.82 ms | 8.76 ms | 17.50 ms | **24.16 ms** | 9.82 | 0% | 100% |
| 3 | 13.28 ms | 9.51 ms | 25.62 ms | **33.31 ms** | 9.81 | 0% | 100% |

- TPS 偏差 < 0.2%，非常稳；
- p95 绝对差只有 13ms，但**相对偏差 62%**——低延迟场景下比值会放大噪声，这是后面门禁取值要注意的点；
- 数据量从 1619 降到 200 后，p95 从 **326ms 级别掉到 26ms 级别**（第一次不受控的冒烟测量见下表对照），
  再次印证"数据量是这轮测试最大的自变量"。

### 负载基线（`02-load-test.js`，20 VU / 3min，读写混合）

| 轮次 | avg | p50 | p90 | **p95** | TPS | 失败率 | checks | iterations |
|------|-----|-----|-----|---------|-----|--------|--------|-----------|
| 1 | 280.24 ms | 141.83 ms | 505.27 ms | **1.02 s** | 13.24 | 0% | 100% | 597 |
| 2 | 280.36 ms | 143.20 ms | 485.60 ms | **1.02 s** | 13.22 | 0% | 100% | 595 |
| 3 | 298.32 ms | 151.95 ms | 530.90 ms | **1.03 s** | 12.80 | 0.08% | 99.92% | 588 |

**偏差对比：**

| 指标 | 受控测量偏差 | 不受控测量偏差 |
|------|-------------|---------------|
| p95 | **±1%** | ±42% |
| TPS | ±3.3% | ±8% |
| 失败率 | 0 ~ 0.08% | 0.14% ~ 0.23% |
| checks | 99.92% ~ 100% | 99.78% ~ 99.86% |

**p95 从平均 1.58s 降到 1.02s（降幅 35%），方差从 42% 收到 1%。**
固定数据集之后，"3 次结果接近"这个稳定性标准才真正满足。

### 基线结论

> **性能基线（受控条件：固定 200 条数据，本机同机压测）**
>
> | 脚本 | 基线 p95 | 基线 TPS | 基线失败率 | 基线 checks |
> |------|---------|---------|-----------|------------|

## 五、门禁推导与落地

### 规则

**门禁 = 基线 × 1.5**，其中负载类指标取"3 次测量中的稳定值"（本次因偏差 ≤1%，直接取 1.02s）。

### 最终门禁值

| 脚本 | 指标 | 基线 | 基线 × 1.5 | **最终门禁** | 差异说明 |
|------|------|------|-----------|------------|---------|
| `01-simple-get.js` | p95 | 26 ms | 39 ms | **< 100 ms** | 见下方"最小容差" |
| | 失败率 | 0% | — | **< 1%** | 沿用通用值 |
| | checks | 100% | — | **> 99%** | 沿用通用值 |
| `02-load-test.js` | p95 | 1.02 s | 1.53 s | **< 1.6 s** | 向上取整到 100ms 刻度 |
| | 失败率 | ≤ 0.08% | — | **< 1%** | 沿用通用值 |
| | checks | ≥ 99.92% | — | **> 99%** | 沿用通用值 |

### 关于"最小容差"（一个必须说清的例外）

冒烟脚本基线 p95 = 26ms，按 ×1.5 得 39ms。但同一脚本的三次测量是 20.5 / 24.2 / 33.3ms——
**基线本身的相对波动就有 62%，39ms 的门禁会被单机噪声直接击穿**，产生假阳性。

比值法（×1.5）的前提是"噪声相对基线很小"。当基线绝对值只有几十毫秒时，这个前提不成立。
所以对低延迟场景补一条规则：

```
门禁 = max(基线 × 1.5, 最小容差)
```

冒烟场景最小容差取 **100ms**：约为基线的 3.9 倍，既能吸收抖动，
也仍能拦住真实劣化——对照表里 1619 条数据时 p95 冲到 326ms，这个门禁照样会红。

### 失败率与 checks 为什么不用乘 1.5

失败率基线是 0%，乘任何系数还是 0，没有意义。这类"正确性指标"直接用通用上限：
失败率 < 1%、checks > 99%。它们的作用是**兜住功能性回归**（比如接口突然开始 500），
和延迟门禁各管一段。

### 关于 checks 与延迟的边界（Day 6 的一处修正）

`01-simple-get.js` 原本有一条 `响应时间 < 200ms` 的逐请求 `check`。它有两个问题：

1. **逐请求断言等价于"max < 200ms"**，比 p95 严格得多，10 VU 下几乎必然有长尾请求超线；
2. 混进 `checks` 后，checks 通过率同时受"功能对不对"和"延迟高不高"两个因素影响，出问题无法定位。

Day 6 已把它移除，改为 thresholds 里的 `p(95)<100ms`。改造后两者的分工是：

| 判定类型 | 放在哪 | 回答的问题 |
|---------|-------|-----------|
| 功能正确性 | `check()` + `checks` 阈值 | 接口返回对了吗？ |
| 性能达标 | `thresholds` | 快不快？够不够快？ |

这与 `02-load-test.js` 的既有设计一致（它本来就只把延迟放在 thresholds）。

## 六、CI 门禁正式启用

Day 3 时，因为基线没建立，CI 里 `k6-load-test` 挂着 `continue-on-error: true` 观察期。
Day 6 基线到位，**已移除 `continue-on-error`，门禁正式生效**：

| Job | 脚本 | 触发条件 | 门禁 | 行为变化 |
|-----|------|---------|------|---------|
| `k6-smoke-test` | `01-simple-get.js` | push、PR | p95<100ms / 失败率<1% / checks>99% | 之前无 thresholds（形同不拦），现在**真的会拦** |
| `k6-load-test` | `02-load-test.js` | 定时、手动 | p95<1.6s / 失败率<1% / checks>99% | 观察期 → **转正，失败即中断流水线** |

k6 的退出码语义保证了这件事：**阈值不通过 → 退出码非 0 → GitHub Actions 步骤失败 → 流水线中断**。

> 启用前请确认：如果你的 CI runner 性能明显不同于本机（本机是 k6 与服务同机争抢 CPU），
> 第一次跑通后建议对着 CI 的实际数据微调门禁值——**门禁是给"当前这套环境"定的**。

## 七、门禁 ≠ SLA（重要区分）

`02-load-test.js` 的门禁是 **1.6s**，但它**不是**对外承诺的服务水平。

| 概念 | 值 | 含义 | 用途 |
|------|-----|------|------|
| **防劣化门禁** | p95 < 1.6s | 相比当前基线劣化 50% 就报警 | CI 阻断，保护"别越来越差" |
| **对外 SLA** | p95 < 500ms | 用户能接受的响应时间 | 业务目标，当前**未达标** |

当前 SLA 未达标的根因是写路径：`create_item` 每次 `sqlite3.connect()` + `commit()`，
SQLite 单写者文件锁把并发写串行化，20 VU 下写请求排队，长尾被拉到秒级。
这在 Day 3 / Day 4 / Day 5 的测量里反复出现（`04-spike-test.js` 尖峰时 p95 甚至到 4.39s）。

处理策略：**先让流水线能用**（基于基线立门禁，拦住劣化），
**Week 2 做完性能优化后，必须回头把门禁收紧到 SLA 水平**。否则这个 1.6s 就成了"技术债的免罪符"。

## 八、基线维护规则

基线不是定一次就永久有效。出现以下情况必须重测：

| 触发条件 | 为什么 |
|---------|-------|
| 被测服务有性能相关变更（含优化上线） | 优化后基线下降，门禁要跟着收紧，否则放任自流 |
| 测试数据集量级变化（如 `GET /items` 加了分页、或种子数据量调整） | 本次已证明数据量是最强自变量 |
| 压测环境变化（换机器、换 CI runner、容器资源限制变化） | 门禁是给特定环境定的 |
| 基线突然漂移但代码没动 | 先查环境（其他进程抢资源、磁盘满、Docker 资源限制），不是先改门禁 |

**重测流程**：固定数据集 → 连跑 3 次 → 偏差 ≤10% 才算稳定 → 取稳定值 ×1.5 → 更新 thresholds → 更新本文档的基线表。
