# 百分位响应时间理解

> Day 1 学习笔记 · Avg/P50/P95/P99 的含义和用途

---

## 一、百分位指标定义

| 指标 | 全称 | 含义 | 关注点 | 典型阈值 |
|------|------|------|--------|----------|
| Avg | Average | 所有请求的平均值 | 整体水平 | < 200ms |
| min | Minimum | 最快的响应时间 | 参考用 | — |
| P50 | Median (50th percentile) | 50% 的请求低于此值 | 普通用户体验 | < 300ms |
| P90 | 90th percentile | 90% 的请求低于此值 | 大多数用户体验 | < 500ms |
| P95 | 95th percentile | 95% 的请求低于此值 | 较差用户体验 | < 1s |
| P99 | 99th percentile | 99% 的请求低于此值 | 最差 1% 用户体验 | < 3s |
| P999 | 99.9th percentile | 99.9% 的请求低于此值 | 极端长尾 | < 10s |
| max | Maximum | 最慢的响应时间 | 极端情况 | 参考用 |

---

## 二、为什么不能只看平均值

### 经典案例

假设 100 个请求：
- 99 个响应时间 = 100ms
- 1 个响应时间 = 10,000ms (10s)

| 指标 | 数值 | 解读 |
|------|------|------|
| Avg | 199ms | 看起来不错？ |
| P50 | 100ms | 一半用户很快 |
| P95 | 100ms | 95% 的用户很快 |
| P99 | 10,000ms | 有 1% 的用户等了 10 秒！ |
| max | 10,000ms | 最慢的请求 |

**结论**：平均值 199ms 看起来可接受，但 P99 暴露了真实的长尾问题。在大流量下，1% 的用户绝对数量也不少（10000 QPS 中 1% = 100 个请求/秒超慢）。

---

## 三、百分位的实际意义

### 用户体验视角

| 百分位 | 代表 | 用户体验 |
|--------|------|----------|
| P50 | 一半用户 | "速度还行" |
| P90 | 大多数用户 | "偶尔有点慢" |
| P95 | 19/20 的用户 | "95% 的人体验OK" |
| P99 | 几乎所有用户 | "只有极少数人体验差" |
| P999 | 极端长尾 | "千分之一的极端情况" |

### 工程实践视角

| 关注点 | 用哪个百分位 | 原因 |
|--------|-------------|------|
| 日常监控 | P95 | 兼顾大多数用户和长尾 |
| SLA 定义 | P99 | 承诺几乎所有人的体验 |
| 极端场景 | P999 | 高并发系统才关注 |
| 快速判断 | P50 + Avg | 粗略了解整体水平 |

## 四、k6 中的百分位配置

```javascript
export const options = {
  thresholds: {
    // P95 响应时间 < 500ms
    http_req_duration: ['p(95)<500'],
    // P99 响应时间 < 2000ms（可选）
    http_req_duration: ['p(99)<2000'],
  },
};
```

k6 输出中的百分位：
```
http_req_duration..............: avg=2.38ms  min=1ms  med=2ms  max=15ms
  p(90)=3ms     p(95)=4ms     p(99)=10ms
```

## 五、百分位与优化的关系

| 现象 | 可能原因 | 优化方向 |
|------|----------|----------|
| P50 低但 P99 高 | 少数请求特别慢 | 查慢查询、GC 停顿、冷启动 |
| P50 和 P99 都高 | 整体性能差 | 优化核心逻辑、加缓存 |
| P95 正常但 P99 突变 | 有极端长尾 | 查超时、锁竞争、连接池耗尽 |
| 随时间 P50 逐渐升高 | 资源泄漏 | 查内存泄漏、连接泄漏 |

---

## 六、一句话总结

> 性能优化不看平均值看 P95/P99——平均值会掩盖长尾问题，P95 代表大多数用户体验，P99 暴露真实的最差体验。在 SLA 中用 P99 承诺，在日常监控中看 P95。
