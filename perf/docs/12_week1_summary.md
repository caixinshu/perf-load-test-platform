## 二、核心重点（必须拎出来记住的）

这些是 Week 1 真正的"骨架"——丢了就串不起来。

### 重点 1：性能测试的"6 × 8 × 6"知识地图

Day 1 学的 6 种测试类型 + 8 步流程 + 6 大核心指标，不是死记硬背，而是**做任何测试前的思考框架**：

- **类型选哪个**（冒烟 / 负载 / 压力 / 尖峰 / 稳定性 / 容量），取决于你的问题是什么（"通不通？"/"够不够？"/"极限在哪？"/"会不会泄漏？"）；
- **8 步流程**里最容易被跳过的是"前置条件检查"——Day 6 第一次测基线就因为没固定数据集，结果漂了 42%；
- **6 大指标**里最容易被误解的是**百分位**：p95 ≠ 95% 的请求 ≤ p95 值，而是"95% 的请求**快于**这个值"。

> 这三个数字（6×8×6）是整个性能测试领域的最小知识集，后续所有深入都是在这个格子里填内容。

### 重点 2：k6 的脚本执行模型

k6 不是"跑脚本"，是**用 VU 模拟真实用户**。理解了这点，很多语法就不用记：

| 概念 | 一句话解释 |
|------|-----------|
| `vus` / `stages.target` | 并发"虚拟用户"数 |
| `duration` / `stages.duration` | 这些 VU 持续工作多久 |
| `export default function()` | 每个 VU 循环执行的"一次用户旅程" |
| `scenarios` + executor | 比 stages 更灵活的负载定义（per-vu-iterations 定迭代数、constant-arrival-rate 定 TPS 等 7 种） |
| `sleep(1)` | 模拟"用户想了 1 秒才点下一步"，去掉就是压力测试 |
| `thresholds` | k6 退出码非 0 的触发器——CI 里用来做性能门禁 |

**最有用的公式**（Day 2 验证过）：`TPS ≈ VU / (平均响应时间 + 思考时间)`
这个公式能反推"我需要多少 VU 才能达到目标 TPS"。

### 重点 3：基线方法论 —— 门禁值不能拍脑袋

Day 6 最核心的收获：**性能门禁 = 实测基线 × 1.5**，三个要素缺一个不行。

| 要素 | Day 6 的教训 |
|------|-------------|
| **实测基线**（不是期望值） | Day 3 把门禁写成 `p(95)<500ms` 是"期望的 SLA"，不是"当前系统能稳定跑到的值"，结果 CI 一直红着 |
| **× 1.5**（留 50% 余量） | 吸收 GC、调度、单机噪声；余量为 0 就天天误报，余量太大就没人拦得住劣化 |
| **受控条件**（环境 / 数据 / 负载都固定） | Day 6 第一次测没固定数据集，基线漂 ±42%；第二次固定后收到 ±1% |

这不是 k6 的规矩，是所有性能测试通用的规矩。后续 Week 2 做性能优化时，优化前后都要回到这条公式上重新验证。

### 重点 4：监控栈的两种数据入口

Prometheus 有两种数据进路，**方向、主动方、适用场景完全不同**，绝不能混：

| 入口 | 谁主动 | 适用 | 我们的用法 |
|------|--------|------|-----------|
| **scrape（抓取）** | Prometheus | 长期驻留的服务（主机、API 服务） | 拉 node_exporter 和自身 |
| **remote write（远程写）** | 客户端 | 短生命周期任务（压测、批处理） | k6 把压测指标推进来 |

为什么 k6 用 remote write 而不是被 scrape：k6 进程只活 30s～3min，Prometheus 15s 一次的抓取大概率抓不到几次，而且 k6 也没有常驻的 `/metrics` 端点。remote write 是唯一合理选项。

### 重点 5：`checks` 与 `thresholds` 的边界

| 判定 | 放哪 | 回答什么问题 |
|------|------|-------------|
| 功能正确性（状态码、返回体结构、字段值） | `check()` + `checks` 阈值 | **"对不对？"** |
| 性能达标（响应时间、失败率） | `thresholds` | **"快不快？够不够？"** |

Day 6 之前 `01-simple-get.js` 有一条 `响应时间 < 200ms` 的逐请求 `check`，混进 checks 后出了问题无法定位——到底是功能错了还是慢了？Day 6 把它移到 thresholds，两条线从此清晰。

### 重点 6：`防劣化门禁 ≠ 对外 SLA`

这组不等式必须写下来，不然 Week 2 优化完容易忘记：

| 概念 | 值 | 含义 | 用途 |
|------|-----|------|------|
| **防劣化门禁** | p95 < 1.6s | 相比当前基线劣化 50% 就报警 | CI 阻断，保护"别越来越差" |
| **对外 SLA** | p95 < 500ms | 用户能接受的响应时间 | 业务目标，当前**未达标** |

当前 SLA 未达标的根因是写路径（SQLite 单写者文件锁）。防劣化门禁只是"先让流水线能跑"，**Week 2 优化后必须回头把门禁收紧到 SLA 水平**——否则 1.6s 就成了技术债的免罪符。

## 三、真正的难点（花了时间才搞明白的）

这些是 Week 1 真正的"坑"——不是因为难，而是因为**不踩一次就想不到问题能藏在这里**。

### 难点 1：基线漂移 —— "系统劣化"其实是"测试输入变了"

**现象**：Day 6 第一次按计划连跑 3 次负载测试，p95 = 1.27s / 1.81s / 1.66s，偏差 ±42%，远超 Day 4 定的 ±10% 稳定线。直觉第一反应是"服务在劣化"。

**根因**：直觉错了。真正的问题是：
1. `02-load-test.js` 有两条写路径（创建商品 + 查询前置创建），每个迭代写入 2 条数据；
2. `GET /items` 是 `SELECT * FROM items` **全表返回、无分页**；
3. 于是数据集从开跑时的 1619 条，3 轮跑完涨到 4867 条——**每一轮的测试输入都比上一轮更重**，p95 上升不是系统劣化，是被测对象状态在变。

**解法**：每轮开跑前把库重置为固定 200 条。收敛效果立竿见影——p95 从平均 1.58s 降到 1.02s，方差从 ±42% 收到 **±1%**。

**教训**：性能测试里，"被测对象的状态"是最容易被忽略的自变量。任何会修改被测对象的测试（写入数据、删除数据、改变缓存状态），都必须在测试之间把它重置回去——否则你测的不是"系统性能"，而是"系统在不断变化的状态下的性能"。

### 难点 2：SQLite 单写者文件锁 —— 写路径为什么会拖垮读路径

**现象**：Day 3 首次负载测试时，20 VU 下读接口 100% 通过，但 **p95 达到 1.27s**，失败率 0.53% 全部集中在写路径；Day 5 尖峰测试 200 VU 时 p95 飙到 **4.39s**，TPS 不升反降。全程 0 失败，说明不是"挂了"，是"排队太长"。

**根因**：`app/main.py` 每来一个请求就 `sqlite3.connect()` + `SELECT`/`INSERT` + `commit()` + `close()`。SQLite 是**单写者**——任何时刻只能有一个写事务拿到文件锁。20 VU 并发下，每条写请求都在前一条 commit 之后才能拿到锁，排队时间直接叠加到响应时间里；同时读请求也被写事务的文件读锁阻塞，尾延迟被拖长。

**为什么这个难点难**：它不报错（HTTP 200 正常返回），失败率也低（因为最终都排到了），**表面看"系统正常"，但 p95 和尖峰行为已经完全不可用**。这是"软瓶颈"——比硬崩溃更难发现，因为需要同时看 **p95 百分位曲线 + 按接口分组的指标**才能定位。

**解法**：留到 Week 2 做。候选方向：SQLite WAL 模式、连接池 / 连接复用、Redis 缓存热点读、写路径异步化。

### 难点 3：低延迟场景的"最小容差"例外

**现象**：冒烟脚本受控基线 p95 = 26ms / 24ms / 20ms（三次）。按公式 `基线 × 1.5` 得 39ms。但单机噪声就有 62% 的相对波动，39ms 的门禁会被本机抖动直接击穿——假阳性。

**根因**：`基线 × 1.5` 这条规则有个隐含前提——"噪声相对基线很小"。当基线绝对值只有几十毫秒时（同机压测、纯读、SQLite 200 条全表扫描），单机的线程调度、GC、操作系统文件缓存命中率差异就能带来 ±10ms 的抖动，这已经占基线的 50% 以上了。

**解法**：补一条规则：

```
门禁 = max(基线 × 1.5, 最小容差)
```

冒烟场景取 **100ms**（约基线 3.9 倍）——既能吸收抖动，也仍能拦住真实劣化（对照实验：数据量 1619 条时 p95 冲到 326ms，这个门禁照样会红）。

**教训**：通用公式永远有边界。基线方法本身告诉你"门禁是基线 × 1.5"，但只有**跑过一次、看过三次的原始数据**，才知道这条公式在低延迟场景下不够用。**经验和理论必须互相验证**。

### 难点 4：Trend 指标的两种 Prometheus 映射 —— 选错了就没有百分位

**现象**：Day 7 写 Grafana 面板时，第一个查询直接写 `k6_http_req_duration_p95`，结果 Prometheus 里根本没有这个指标名。

**根因**：k6 的 `http_req_duration` 是 **Trend 类型**（统计分布）。当用 `--out experimental-prometheus-rw` 推进 Prometheus 时，有两种映射模式：

| 模式 | 开关 | 产出 | 能算任意百分位吗 |
|------|------|------|----------------|
| 默认（Counter + Gauge） | 无 | `k6_http_req_duration_p99`（固定分位，默认只有 p99） | ❌ 只能看预设的 |
| **native histogram** | `K6_PROMETHEUS_RW_TREND_AS_NATIVE_HISTOGRAM=true` | `k6_http_req_duration_seconds`（直方图） | ✅ `histogram_quantile()` 想要几分位都行 |

默认模式是"凑合能用"，但在 Grafana 面板里**没法动态调整 p95 / p99 / p999**，也没法按标签（`name=listItems` / `name=createItem`）拆开看。必须上 native histogram。

**两个开关缺一不可**：
- k6 侧：`K6_PROMETHEUS_RW_TREND_AS_NATIVE_HISTOGRAM=true`
- Prometheus 侧：`--enable-feature=native-histograms`

**为什么这个难点难**：k6 官方文档里这两条是分散在不同页面的，`experimental-prometheus-rw` 页面讲的是映射规则，native histogram 的开关在 Prometheus 启动参数文档里。**少查任何一个，面板就做不出来**。

### 难点 5：本机没有 Docker —— 监控栈只能"写配置不能跑"

**现象**：Day 7 写完整套 `monitoring` profile（Prometheus / Grafana / node_exporter），`docker compose --profile monitoring up -d` 在本机执行直接报 `docker 命令不存在`。

**根因**：本机是 Windows，没装 Docker Desktop。而 node_exporter、Grafana、实验性的 `--enable-feature=native-histograms` 开关都是容器化环境最方便跑的。

**解法**：接受这个限制，监控栈的**端到端链路放在 CI 上验证**。CI 的 `k6-load-test-prometheus` job 会起 monitoring profile + k6 remote write，跑完还会断言指标真的进了 Prometheus。本机只负责：
- 配置文件语法校验（Python YAML + JSON 解析）；
- 把面板 JSON 里的 datasource uid 固定成 `prometheus`（和 provisioning 里的 uid 对齐，避免 Grafana 导入时 datasource not found）；
- 把 Grafana provisioning 的路径、profile 配置都按容器里的路径写死。

**教训**：开发环境和生产环境能力不对等时，**不要硬逼自己在受限环境里把链路跑通**——既浪费时间，也容易为了绕开限制写出和生产不一样的配置。正确做法是：配置按生产写好，在有能力的环境（CI）里验证，受限环境只做静态校验。

### 难点 6：逐请求延迟断言 —— 该放进 `checks` 还是 `thresholds`

**现象**：Day 6 之前 `01-simple-get.js` 里有一条 `响应时间 < 200ms` 的逐请求 `check`。数据量 1619 条时 checks 掉到 96%——不是接口错了，是读一个 4867 条的全表确实超过 200ms。但看到 checks 红了，直觉第一反应是"功能挂了"。

**根因**：逐请求 `check` 本质上是"**max < 200ms**"（任何一个请求超时就红），比 p95 严格得多。而且混进 `checks` 阈值后，**checks 通过率同时受功能和延迟两个因素影响**——出问题无法定位。

**解法**：把逐请求延迟断言删掉，改成 `thresholds` 里的 `p(95)<100ms`。这样：
- checks 只管"返回对不对"（状态码、数据结构）；
- thresholds 只管"够不够快"（p95、失败率）；
- 两者各管一段，CI 红灯时能直接定位是"功能回归"还是"性能劣化"。

**教训**：**断言粒度决定了问题定位粒度**。粗粒度的（p95、全局通过率）适合 thresholds 做门禁，细粒度的（每请求都要对、每个字段都要对）适合 checks 做功能校验。混在一起就是给故障排查制造烟雾弹。

## 四、Week 2 衔接 —— 哪些坑还要继续补

## 五、一句话收尾

> Week 1 最大的收获不是"学会了 k6 的语法"，而是**第一次用一个受控的、可重复的方法回答了"我们的系统到底有多快"这个问题**。所有的难点（基线漂移、软瓶颈、低延迟例外、native histogram 开关）都是"答案"的一部分——每踩一个坑，就往"真正理解了自己的系统"近一步。
