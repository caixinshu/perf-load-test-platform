# 21. 全链路性能分析实战（Week 3 Day 18）

## 一、全链路压测的核心价值

> 不是「知道系统慢」，而是「知道系统为什么慢、慢在哪」。

单体压测只能看到一个接口的响应时间，但无法回答：
- 这个接口慢，是数据库慢还是下游服务慢？
- 错误率上升，是哪个服务先出的问题？
- 全链路中，哪个节点是真正的瓶颈？

**全链路压测 = 模拟真实用户行为比例 + 链路追踪定位瓶颈**

## 二、业务模型设计

真实用户行为不是均匀的：浏览的人多、下单的人少、查订单的更少。这个比例叫「业务模型」。

| 行为 | 占比 | 接口链路 | 经过节点 |
|------|------|---------|---------|
| 浏览商品 | 60% | `GET /products?page=` + `GET /products/{id}` | gateway → product → db/cache |
| 下单购买 | 25% | `GET /products/{id}` + `POST /orders` | gateway → order → product → db/cache → order → db |
| 查询订单 | 15% | `GET /orders/{id}` | gateway → order → db |

### 为什么是 60/25/15？

- 电商典型漏斗：浏览 → 加购 → 下单 → 支付，转化率逐级下降
- 浏览是高频轻量操作，下单是低频重操作（写库 + 跨服务调用）
- 比例越接近真实，压测结果越有参考价值

## 三、压测脚本：阶梯式加压

```javascript
stages: [
  { duration: '1m', target: 100 },  // 爬升
  { duration: '3m', target: 100 },  // 稳定：观察常态性能
  { duration: '1m', target: 200 },  // 加压
  { duration: '2m', target: 200 },  // 高压：观察极限性能
  { duration: '1m', target: 0 },    // 下降
]
```

**两段稳定负载的意义**：
- 100 VU 稳定 3 分钟：模拟日常流量，看常态指标
- 200 VU 稳定 2 分钟：模拟大促流量，看极限指标

## 四、Jaeger 链路分析 6 个维度

压测结束后，在 Jaeger 中找几个慢的 trace，从以下 6 个维度分析：

### 维度 1：总耗时分布
看 trace 的总 duration，定位是「个别慢」还是「整体慢」。
- 个别慢 → 可能是偶发的 GC、锁竞争、缓存未命中
- 整体慢 → 系统性瓶颈（CPU 满、连接池满、DB 慢查询）

### 维度 2：Span 耗时占比
看 trace 中每个 span 的耗时占比，找到最耗时的环节。

```
POST /orders (800ms)
  ├── order-service 内部处理 (50ms, 6%)
  ├── GET /products/1 → product-service (150ms, 19%)
  │     └── product DB SELECT (140ms, 18%)
  └── order DB INSERT (600ms, 75%)  ← 瓶颈在这里！
```

### 维度 3：服务间调用延迟
看 HTTP 调用 span 的 duration，判断是「网络慢」还是「对端处理慢」。

| Span 标签 | 含义 |
|-----------|------|
| `http.method` / `http.url` | 调用的接口 |
| `http.status_code` | 返回状态码 |
| `db.system` / `db.statement` | 数据库操作 |
| `net.peer.name` / `net.peer.port` | 对端地址 |

### 维度 4：数据库操作
看 DB span 的 `db.statement`，定位慢 SQL。
- SELECT 全表扫描 → 加索引
- INSERT 慢 → 检查连接池、批量写入、磁盘 IO

### 维度 5：并发与等待
看同一 trace 中是否有并行 span，以及是否有明显的等待间隙。
- 并行 span 之间有大间隙 → 可能是锁等待、连接池等待
- 串行 span 很多 → 考虑并行化优化

### 维度 6：错误与异常
看 span 中的 `error: true` 标记和异常日志。
- 某个服务大量 error → 该服务是故障源
- DB connection timeout → 连接池不够

## 五、瓶颈定位实战：3 个典型场景

### 场景一：慢 SQL

**操作**：给订单服务的 `GET /orders/{id}` 加一个 `pg_sleep(1)` 的慢 SQL。

**Jaeger 现象**：
```
GET /orders/1 (1020ms)
  └── order DB SELECT (1010ms)  ← 这个 span 占了 99% 时间
```

**定位**：DB span 耗时异常高，`db.statement` 显示 `SELECT ... pg_sleep(1)`。

**修复**：去掉 `pg_sleep`，优化 SQL（加索引、避免全表扫描）。

### 场景二：缓存失效

**操作**：把商品服务的 Redis 缓存关掉（`GET /products/{id}` 直接查 DB）。

**Jaeger 现象**：
```
缓存开启时：
GET /products/1 (5ms)
  └── cache GET (2ms)  ← 缓存命中

缓存关闭后：
GET /products/1 (80ms)
  └── product DB SELECT (78ms)  ← 每次都查库
```

**定位**：对比开启/关闭缓存的 trace，DB span 从 2ms 变成 78ms，缓存命中消失。

**修复**：恢复缓存，检查缓存 TTL 和淘汰策略。

### 场景三：连接池耗尽

**操作**：把商品服务的数据库连接池上限设为 2，同时加压到 200 VU。

**Jaeger 现象**：
```
GET /products/1 (2500ms)
  └── product DB SELECT (2480ms)  ← 大部分时间在等连接
```

服务日志会出现：
```
psycopg2.OperationalError: connection pool exhausted
```

**定位**：DB span 耗时高但 SQL 本身不慢（在 DB 端执行很快），说明时间花在**等待获取连接**上。

**修复**：增大连接池，或优化 SQL 减少连接占用时间。

## 六、压测 + 监控联调流程

压测时同时打开 3 个面板：

| 面板 | 工具 | 观察重点 |
|------|------|---------|
| 系统资源 | Grafana | 哪个服务 CPU/内存先打满 |
| 接口指标 | k6 输出 | 哪个接口 P95 先恶化、错误率何时上升 |
| 链路追踪 | Jaeger | 慢 trace 的 span 耗时分布 |

### 观察清单

- [ ] 哪个服务的 CPU 先到 80%？
- [ ] 哪个接口的 P95 最先超过阈值？
- [ ] 错误率从哪个 VU 量级开始上升？
- [ ] 数据库连接数是否打满？
- [ ] Redis 命中率是否下降？
- [ ] Jaeger 中最慢的 span 属于哪个服务？

## 九、踩坑记录

| 问题 | 原因 | 解决 |
|------|------|------|
| 下单大量 400 | 商品库存不足（product stock 有限） | 压测脚本用 product_id 1-50，避免超库存 |
| 查订单 404 | 订单 ID 随机，可能不存在 | check 允许 200 或 404 |
| Jaeger 看不到 trace | thrift UDP 6831 兼容性问题 | 改用 OTLP gRPC 4317 |
