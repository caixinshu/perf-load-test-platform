# 08 - 性能指标解读与分析（Day 4）

> 目标：建立系统化的性能分析思维框架，能看懂 k6 输出的每一个指标，能判断系统瓶颈在哪里、瓶颈有多严重，以及下一步该如何优化。

---

## 一、性能分析 5 步法（核心方法论）

拿到一份压测报告，按以下顺序思考，不要一上来就看平均响应时间：

1. **看错误率** — `http_req_failed` rate 是否为 0？`checks` pass rate 是否 100%？
   - 错误率 > 0.1%：系统已经在拒绝请求，先解决正确性，再谈性能。
   - 错误率 = 0：系统没有崩，可以继续看延迟和吞吐。

2. **看吞吐量** — `http_reqs` rate（TPS）是多少？是否随 VU 增长而线性增长？
   - TPS 随 VU 线性增长 → 还没到瓶颈，系统还有余量。
   - TPS 停止增长 → 已到吞吐量极限，这是真正的"瓶颈点"。

3. **看延迟百分位** — 看 `p(90)` / `p(95)` / `p(99)`，**不要只看 avg**。
   - avg 会被长尾拉偏或被大量快请求稀释。
   - p95 代表"95% 的用户感受到的延迟"，是 SLA 的核心指标。

4. **找拐点** — 对比不同 VU 级别下的 TPS 和 p95。
   - TPS 拐点：VU 增加但 TPS 不再涨的那个 VU 数。
   - 延迟拐点：p95 开始急剧上升的那个 VU 数。
   - 两个拐点通常出现在同一个点附近。

5. **定结论** — 系统的**容量上限**是多少？**安全运行区间**是多少？瓶颈在哪一层？

## 二、百分位指标详解表

| 指标 | 含义 | 本次基线实测 | 典型判断标准 |
|------|------|------------|------------|
| `avg` | 所有请求的平均耗时 | 126 ms | 容易被极端值干扰，仅作参考 |
| `med` (p50) | 50% 请求的耗时低于此值 | 57 ms | 代表"典型用户"体验 |
| `p(90)` | 90% 请求低于此值，10% 高于 | 304 ms | 内部系统常用的 SLA 线 |
| `p(95)` | 95% 请求低于此值 | 446 ms | **对外服务最常用的 SLA 线** |
| `p(99)` | 99% 请求低于此值 | ~1.5 s（从 max 估算） | 金融/支付类核心链路用 |
| `max` | 最慢的一次请求 | 1.5 s | 排查长尾问题用，不做 SLA |

**为什么不能只看 avg？**

假设 100 次请求，99 次耗时 10ms，1 次耗时 10s：
- avg = (99×10 + 10000) / 100 = 109.9 ms（看起来不错）
- p99 = 10000 ms（1% 用户等了 10 秒，体验极差）

生产环境中，**p95 才是用户真实感受到的性能**。

## 三、性能基线数据（10 VU / 1 分钟，3 次重复）

脚本：`perf/scripts/baseline.js`，场景：10 并发用户，持续 1 分钟，混合调用 health / listItems / createItem 三个接口。

### 3 次原始数据

| 指标 | Run 1 | Run 2 | Run 3 | 偏差 |
|------|-------|-------|-------|------|
| iterations | 208 | 210 | 207 | ±1.4% |
| TPS (req/s) | 10.02 | 10.04 | 9.95 | ±0.5% |
| avg duration | 127.2 ms | 118.5 ms | 134.5 ms | ±6% |
| p50 (med) | 40.1 ms | 50.1 ms | 80.8 ms | ±35%（波动大） |
| p90 | 330.6 ms | 270.6 ms | 311.3 ms | ±9% |
| p95 | 483.8 ms | 359.2 ms | 495.6 ms | ±17% |
| max | 1.45 s | 1.63 s | 1.44 s | ±6% |
| checks pass | 100% | 100% | 100% | — |
| 失败率 | 0% | 0% | 0% | — |

### 基线结论

3 次 TPS 偏差 < 1%，说明数据稳定，可作为基线：

> **性能基线（10 VU 混合场景）：**
> - TPS = **10.0 req/s**
> - p50 ≈ **57 ms**，p90 ≈ **304 ms**，p95 ≈ **446 ms**
> - 错误率 = **0%**，checks = **100%**
> - 单次迭代含 3 个请求 + 2.5s sleep，因此 TPS 较低属正常。

**观察**：p95 已经到 450ms，而 p50 仅 57ms——说明存在明显的长尾。这是写接口（createItem）触发 SQLite 锁竞争导致的，读接口（health/list）很快。

## 四、压力测试结果（50 → 500 VU 阶梯加压）

脚本：`perf/scripts/stress-test.js`，场景：只压 GET /items（纯读），无 sleep，每级 1 分钟，逐级 50→100→200→300→500 VU。

### 整体结果

| 指标 | 值 |
|------|-----|
| 总请求数 | 9,259 |
| 整体 TPS | 27.9 req/s |
| avg duration | 7,009 ms |
| p50 (med) | 6,220 ms |
| p95 | 14,403 ms |
| max | 34.6 s |
| checks pass | 100%（9,259/9,259） |
| 失败率 | 0% |

### 各 VU 档位的 TPS 分布

| VU 范围 | 平均 TPS | 解读 |
|---------|---------|------|
| 0 - 49 | 17.6 req/s | TPS 随 VU 增长，未饱和 |
| 50 - 99 | 30.7 req/s | **到达吞吐量上限** |
| 100 - 149 | 29.8 req/s | 不再增长 |
| 150 - 199 | 30.0 req/s | 不再增长 |
| 200 - 249 | 32.1 req/s | 不再增长 |
| 250 - 299 | 31.4 req/s | 不再增长 |
| 300 - 349 | 28.2 req/s | 不再增长 |
| 350 - 399 | 31.7 req/s | 不再增长 |
| 400 - 449 | 31.6 req/s | 不再增长 |
| 450 - 499 | 30.1 req/s | 不再增长 |
| 500 - 549 | 30.1 req/s | 不再增长 |

### 关键结论

1. **极限 TPS ≈ 30 req/s**：VU 从 50 涨到 500（10 倍），TPS 始终卡在 30 左右，不再增长。
2. **拐点在 50 VU**：50 VU 之后 TPS 停止增长，系统已饱和。
3. **延迟随 VU 线性上升**（符合 Little's Law：`RT = VU / TPS`）：
   - 50 VU 时预期 RT ≈ 50 / 30 ≈ 1.7 s
   - 500 VU 时预期 RT ≈ 500 / 30 ≈ 16.7 s（实测 p95 = 14.4 s，吻合）
4. **系统没有崩溃**：全程 0 失败、checks 100%——SQLite 用排队代替拒绝，请求都成功了，只是慢。

## 五、瓶颈根因分析

### 现象
500 VU 压测下，TPS 不涨、延迟飙升，但无任何报错。

### 根因（结合代码 `app/main.py`）

```python
@app.get("/items")
def list_items():
    conn = sqlite3.connect(DB_PATH)   # ← 每个请求都新建连接
    try:
        cursor = conn.execute("SELECT * FROM items")
        return [dict(r) for r in cursor.fetchall()]
    finally:
        conn.close()                   # ← 立刻关闭
```

问题链：

1. **每次请求都 `sqlite3.connect()` + `close()`**：SQLite 是文件数据库，每次打开/关闭文件有 IO 开销，且无法复用连接池。
2. **SQLite 文件级锁**：虽然是读请求，但所有读操作共享同一个文件句柄的打开/关闭，加上 Python GIL 和 uvicorn 的单 worker，并发被串行化。
3. **无连接池、无异步 I/O**：uvicorn 同步模式下，每个请求占满一个工作线程，500 个并发请求全部排队。

### 优化方向（后续 Day 会落地）

| 优化手段 | 预期提升 |
|---------|---------|
| 改为 FastAPI 异步 + `aiosqlite` | 提升并发 |
| 使用连接池（复用 DB 连接） | 减少 connect 开销 |
| 把 SQLite 换成 PostgreSQL/MySQL | 消除文件锁瓶颈 |
| 引入 Redis 缓存热点数据 | 降低 DB 压力 |

## 六、性能分析思维训练：4 种典型现象的判断思路

### 现象 1：VU 增加，TPS 线性增长，p95 稳定
- **判断**：系统还有余量，未到瓶颈。
- **行动**：继续加压，直到找到拐点。

### 现象 2：VU 增加，TPS 不再增长，p95 线性上升（= 本次实测）
- **判断**：已到吞吐量极限，瓶颈在服务端（DB / CPU / 锁）。
- **行动**：定位瓶颈层，考虑横向扩容或优化算法。

### 现象 3：错误率开始飙升，p95 也上升
- **判断**：系统已经过载，开始拒绝请求。
- **行动**：这是"硬性极限"，需要在这个 VU 数的 70% 以下运行，或加限流。

### 现象 4：TPS 和 p95 都正常，但 CPU 已 100%
- **判断**：CPU 是瓶颈，即将触顶。
- **行动**：加机器 / 换更高效的算法 / 优化热路径代码。

### 本次对应哪种现象？
**现象 2**（软瓶颈）。系统没有拒绝请求，但吞吐被锁死，延迟排队。这种现象的危险在于：从监控看"一切正常"（无报错），但用户已经感受到严重卡顿。**只看错误率会漏判**，必须同时看 TPS 和 p95。
