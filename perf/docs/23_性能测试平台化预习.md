## 一、性能测试平台的核心功能

个人跑 k6 脚本和企业级性能测试平台的差距在哪？平台化要解决的核心问题是：**让性能测试可复用、可追溯、可自动化、可对比**。

| 模块 | 功能 | 解决的问题 |
|------|------|-----------|
| **场景管理** | 压测场景的 CRUD、版本管理、参数化配置 | 脚本散落在各处，无法复用 |
| **数据管理** | 测试数据集的上传、清洗、分片 | 每次压测手动准备数据 |
| **压测执行** | 分布式 k6 集群调度、实时监控 | 手动起容器、手动看日志 |
| **报告管理** | 结果自动生成、历史对比、趋势分析 | 结果散落，无法对比 |
| **告警通知** | 阈值告警、飞书/钉钉推送 | 出问题没人知道 |
| **权限管理** | 团队/项目隔离、操作审计 | 多人协作混乱 |

## 二、k6 与 CI/CD 的集成方式

### 2.1 三种集成模式

| 模式 | 适用场景 | 实现方式 |
|------|---------|---------|
| **本地脚本 + CI 触发** | 小团队、快速上手 | GitHub Actions 里 `k6 run`，结果推 Grafana |
| **k6 Cloud** | 中大型团队 | k6 官方 SaaS，全球分布式节点，开箱即用 |
| **自建平台 + k6 Operator** | 大型企业 | Kubernetes 上部署 k6 Operator，CRD 管理压测任务 |

### 2.2 GitHub Actions 集成（本项目已实践）

```yaml
# CI 中跑 k6 并断言性能门禁
- name: Run k6 load test
  run: k6 run --summary-export=summary.json scripts/load-test.js

- name: Performance gate
  run: |
    p95=$(python -c "import json; print(json.load(open('summary.json'))['metrics']['http_req_duration']['values']['p(95)'])")
    if (( $(echo "$p95 > 800" | bc -l) )); then
      echo "FAIL: p95=$p95 > 800ms"; exit 1
    fi
```

### 2.3 k6 Operator（K8s 原生方案）

```yaml
apiVersion: k6.io/v1alpha1
kind: TestRun
metadata:
  name: full-link-test
spec:
  parallelism: 3
  script:
    configMap:
      name: k6-scripts
      file: full-link-load-test.js
  arguments: --out experimental-prometheus-rw
  separate: false
```

## 三、性能门禁（Performance Gate）

### 3.1 什么是性能门禁

在 CI/CD 流水线中设置**自动化的性能阈值检查**，性能不达标就**阻断发布**。和单元测试门禁、安全门禁并列，是质量门禁的一种。

### 3.2 门禁类型

| 类型 | 阈值 | 说明 |
|------|------|------|
| **响应时间门禁** | p95 < 800ms | 超过就 fail |
| **错误率门禁** | rate < 1% | 超过就 fail |
| **回归门禁** | p95 涨幅 < 20% | 和基线对比，劣化超 20% fail |
| **资源门禁** | CPU < 80%, 内存 < 85% | 资源超限 fail |

### 3.3 门禁设计原则

1. **基线先行**：先建立稳定基线，门禁阈值 = 基线 × 容差系数
2. **分层设置**：冒烟门禁（严）、负载门禁（中）、压力门禁（宽）
3. **渐进式**：先告警不阻断，稳定后再阻断
4. **可豁免**：支持人工审批豁免，但留痕

### 3.4 本项目已实现的门禁

- `01-simple-get.js`：p95 < 100ms（冒烟门禁）
- `db-stress-test.yml`：p95 < 1500ms + 错误率 < 5%（CI 门禁）
- `full-link-test.yml`：p95 < 800ms + 错误率 < 3%（CI 门禁）

## 四、如果要做一个性能测试平台，需要哪些模块？

```
┌─────────────────────────────────────────────────┐
│                   前端 (React/Vue)                │
│   场景管理 │ 数据管理 │ 报告中心 │ 实时监控 │ 告警  │
├─────────────────────────────────────────────────┤
│                   后端 API (FastAPI)               │
│   场景服务 │ 数据服务 │ 执行调度 │ 报告服务 │ 告警服务 │
├─────────────────────────────────────────────────┤
│              执行层 (k8s / Docker)                 │
│   k6 Worker 集群 │ Prometheus │ Jaeger │ Grafana   │
├─────────────────────────────────────────────────┤
│              存储层                                │
│   PostgreSQL(元数据) │ Redis(队列) │ S3(报告)      │
└─────────────────────────────────────────────────┘
```

### 核心模块拆解

1. **场景服务**：管理压测脚本、参数、阈值，支持版本
2. **数据服务**：管理测试数据集，支持参数化
3. **执行调度服务**：
   - 接收压测任务，分发到 k6 Worker
   - 管理 Worker 生命周期（创建/销毁）
   - 实时采集 k6 指标
4. **报告服务**：
   - 压测结束后自动生成报告
   - 历史结果对比、趋势图
5. **告警服务**：
   - 阈值检查（性能门禁）
   - 飞书/钉钉/邮件通知
